# User Journey

## Purpose

This document defines the ideal experience of a visitor interacting with the portfolio.

The goal is to ensure every section of the portfolio has a purpose and contributes to a cohesive journey.

This document focuses on user experience rather than implementation.

---

# Primary User

The primary user is a recruiter, engineering manager, or technical interviewer who has between **2 and 5 minutes** to evaluate the portfolio.

The experience should help them quickly understand:

- Who the developer is.
- What they build.
- How they solve problems.
- Why they should schedule an interview.

---

# User Journey

---

## Stage 1 — Arrival

### User Goal

Determine whether the portfolio is worth exploring.

### User Questions

- Who is this person?
- Is this a software engineer?
- Does this feel professional?

### Product Responsibility

Immediately communicate:

- Professionalism
- Technical focus
- High quality

### Success Criteria

The visitor decides to continue scrolling.

---

## Stage 2 — First Impression

### User Goal

Understand the developer within a few seconds.

### User Questions

- What kind of engineer is this?
- What technologies do they work with?
- What makes them different?

### Product Responsibility

The Hero section should answer these questions quickly.

Avoid long paragraphs.

Provide clear actions such as:

- Resume
- GitHub
- LinkedIn
- Explore Projects

### Success Criteria

The visitor understands the purpose of the portfolio.

---

## Stage 3 — Curiosity

### User Goal

Discover interesting projects.

### User Questions

- What has this developer actually built?
- Which project should I explore first?

### Product Responsibility

Use the Featured Project and Project Gallery to encourage exploration.

Projects should be the primary focus.

### Success Criteria

The visitor opens at least one project page.

---

## Stage 4 — Evaluation

### User Goal

Judge technical ability.

### User Questions

- How difficult was this project?
- What challenges were solved?
- How does this developer think?

### Product Responsibility

Every project page should clearly explain:

- Problem
- Research
- Architecture
- Technical decisions
- Trade-offs
- Challenges
- Results

### Success Criteria

The visitor gains confidence in the developer's engineering ability.

---

## Stage 5 — Verification

### User Goal

Confirm credibility.

### User Questions

- Are these achievements genuine?
- Is there proof?
- Can I verify the work?

### Product Responsibility

Display:

- GitHub repositories
- Live demos
- Certificates
- Publications
- Screenshots
- Achievement proofs

### Success Criteria

The visitor trusts the portfolio.

---

## Stage 6 — Connection

### User Goal

Contact the developer.

### User Questions

- How do I reach them?
- Can I view more work?

### Product Responsibility

Provide a simple contact section with:

- LinkedIn
- GitHub
- Email

The tone should feel welcoming rather than formal.

### Success Criteria

The visitor knows exactly how to connect.

---

# Emotional Journey

The portfolio should guide visitors through the following emotions.

Arrival

↓

Curiosity

↓

Interest

↓

Confidence

↓

Trust

↓

Action

---

# Friction Points

The portfolio should avoid:

- Information overload
- Long paragraphs
- Slow loading
- Confusing navigation
- Excessive animations
- Hidden interactions
- Unclear project descriptions

---

# UX Principles

The portfolio should:

- Reward curiosity.
- Keep navigation effortless.
- Make projects easy to discover.
- Prioritize readability.
- Keep interactions subtle.
- Reduce cognitive load.
- Maintain consistency.

---

# Definition of Success

A successful visitor journey ends with at least one of the following outcomes:

- Resume viewed.
- GitHub visited.
- LinkedIn profile opened.
- Project case study explored.
- Contact initiated.

If one or more of these actions occurs, the portfolio has achieved its purpose.
